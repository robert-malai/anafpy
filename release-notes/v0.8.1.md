# anafpy 0.8.1 — fresh installs work again

## Fix

**A fresh `pip install anafpy[mcp]` had been broken since 2026-07-28.** That day
the official MCP Python SDK released its v2.0.0, and `pip install mcp` started
resolving to it. v2 removes the `mcp.server.fastmcp` module — the `FastMCP`
class anafpy's server was built on is now `mcp.server.MCPServer` — and anafpy's
dependency said only `mcp>=1.10`, so a new environment got the new SDK and the
server died at import before serving a single tool. Environments installed
earlier, or pinned by a lock file, never noticed; every install made after the
SDK's release did.

0.8.1 migrates to the v2 SDK rather than pinning it out. The v1 line is now in
maintenance mode — security fixes only — so a `<2` cap would only have deferred
this same port to a worse moment. The dependency is now `mcp>=2,<3`.

Nothing changes at the tool surface. The port is the SDK's own rename and its
snake_case pass over the protocol types: the server class, the
`ToolAnnotations` fields, and the shapes the tests assert against. The wire
format was camelCase before and stays camelCase — v2 keeps it behind field
aliases — so every tool, resource, prompt, description, and annotation ships
exactly as it did in 0.8.0. A v2 server also still serves 2025-era MCP clients
from the same stdio process, negotiated per connection, so existing Claude
Desktop configurations keep working without any change on the user's side.

Two dependency notes ride along. The v2 SDK dropped `pydantic-settings` from
its own dependency set; anafpy has always declared it directly (the server's
`ServerConfig` is built on it), so nothing moves — it is just no longer an
accident of the SDK's tree that it is present. And the SDK's HTTP stack now
runs on `httpx2`, its next-generation fork of httpx; that arrives as a
transitive dependency of the SDK alone, and the anafpy clients themselves stay
on plain `httpx` exactly as before.

## Verified

The full respx suite passes against the v2 SDK unchanged apart from the
renames, and the shipped server was smoke-tested end to end over real stdio: a
v2 client launched `python -m anafpy.mcp` as a subprocess, negotiated the
handshake, listed the 46 tools and 25 reference resources, and called
`auth_status` with its structured output intact.

## Not yet verified

**A live session under Claude Desktop has not been re-run on this build.** The
dual-era claim — a v2 server serving a 2025-era client — is the SDK's own,
covered by its conformance suite, and the stdio smoke above exercised the same
server process; but the first real Claude Desktop conversation on 0.8.1 is
still ahead. If a configured server goes silent after the upgrade, the ask is
the usual one: an issue with the host's MCP log attached.
