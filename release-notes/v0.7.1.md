# anafpy 0.7.1 — two ways ANAF answers 200 and means "no"

Both fixes here are the same shape: an HTTP 200 whose body is not the thing you asked for. One was being handed back as a result; the other was raised so vaguely that callers had to substring-match Romanian prose to know whether to try again. Neither is anafpy inventing policy — both wordings were observed in production archives this month, and both are now recorded in the [reference](https://anafpy.readthedocs.io/en/latest/anaf-reference/efactura/api/).

## Fix

**A firewall block page could be written to disk as a PDF.** ANAF fronts `webservicesp.anaf.ro` with an F5 that scans the invoice XML you post to `validare`/`transformare` and answers a `Request Rejected` HTML page — with **HTTP 200** — when the document matches an attack signature. That page is neither PDF bytes nor ANAF's JSON error shape, so `render_invoice_pdf` returned it as if it were a render result, and a caller who trusted the return value saved HTML under a `.pdf` name.

Legitimate documents trip it: 4 of ~525 archived inbound messages, from 3 unrelated issuers, deterministically. A *relative* path in `xsi:schemaLocation` reads as path traversal, and `;CP ` in a street address (`Loc.Periam Nr. 868;CP 307315`) matches a shell-command signature.

The block page now raises `AnafWafRejectionError`, carrying the F5 support id to quote to ANAF. It is raised from the shared transport, so every client is covered and no caller has to sniff for `%PDF` to tell success from refusal — this is ANAF's infrastructure refusing the call, never a verdict on the document.

Two accommodations follow the wire. `xsi:schemaLocation` is stripped before posting to both document services: it is advisory, the rendered PDF is byte-identical without it, and it is the bait one class of issuing software emits on every document it writes. And a block on the `/DA` (skip-validation) path is retried once on the validating path, which carries the looser policy of the two — the narrow exception to "discrete methods do no transport retry", justified by a different URL on a stateless public service that files nothing, weighed against losing the artifact for a document ANAF itself already accepted. The retry warns, so a caller who asked to skip validation learns ANAF validated after all.

Live-verified 2026-07-30 on the four real invoices: three render via the strip alone, the fourth via the fallback. Established in the same session and recorded in reference §6.1 — the OAuth host does not share the policy, so **filing is unaffected**; `validare` passes what `/DA` blocks; and XML character references do not fool the WAF (`&#32;` for the space is still blocked), so anafpy deliberately leaves content signatures alone rather than rewriting what the PDF displays.

Reported as issue #10.

**"The download window closed" is no longer told the same way as "try again".** `descarcare` answers HTTP 200 with a JSON note instead of the ZIP for two conditions with opposite meanings: an unknown id or malformed request, worth retrying or fixing, and a message that aged out of ANAF's 60-day window, which is gone for good. Both raised a bare `AnafResponseError`, so telling them apart meant matching Romanian text out of `str(exc)` — and that vocabulary is anafpy's job, not the caller's.

`AnafDownloadExpiredError` now carries the terminal case, with the id on `message_id`, so an archiver can skip a message permanently:

```python
try:
    message = await client.download(item.id)
except AnafDownloadExpiredError:
    mark_permanently_unavailable(item.id)  # never ask again
```

You meet this without any caller error: `listaMesaje` and `descarcare` anchor their 60 days differently, so ANAF lists messages it then refuses to hand over, and any 60-day lookback meets the boundary band. Observed on 3 messages of a client archive.

The recognizer under-matches by design — a false positive loses an invoice once the real window shuts. It parses the body and reads the `eroare` field rather than the composed message, matches one accent-stripped core clause instead of the whole sentence (ANAF rewords), and falls through to the plain `AnafResponseError` on any parse failure, missing field, or unrecognised wording.

Both new classes subclass `AnafResponseError`, so code that already catches that keeps working — and every `tenacity` predicate in the tree already excludes it, so a terminal condition cannot become retryable by inheritance.

## Not yet verified

**No live tripwire watches the closed-window wording.** The four firewall cases are covered by two live tests — that such a document still renders, and that the firewall still blocks it at all — so a policy change on ANAF's side surfaces on demand. The expiry note has no equivalent: it was live-observed on a real archive, but reproducing it requires a message at the far edge of the 60-day window, which no test can conjure. If ANAF rewords the clause, `download` quietly reverts to raising the generic `AnafResponseError` — a caller that retries forever on a file that will never come back, rather than a wrong terminal verdict. That is the failure direction chosen on purpose.
