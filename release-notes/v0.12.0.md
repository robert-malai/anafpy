# anafpy 0.12.0 — the Windows extension brings its own curl

Windows users no longer have to install Git for Windows to log in to SPV or
the declaration portal. The `anafpy-win32-x64.mcpb` bundle now carries its
own curl, and the certificate logins use it instead of the one Windows
ships.

## Why the computer's own curl was the problem

The SPV and declaration-portal logins are the one place anafpy cannot use
Python's networking: a qualified certificate's key is non-exportable, so
CPython's `ssl` cannot present it, and the handshake runs through curl
against the platform key store instead. On macOS that is `/usr/bin/curl`
and it works. On Windows the built-in curl is the part that breaks, in two
ways we have watched fail live:

- `System32\curl.exe` versions **8.13–8.15** carry a Schannel regression
  ([curl#18029](https://github.com/curl/curl/issues/18029)) that kills
  ANAF's mid-connection TLS renegotiation — the login dies with
  `SEC_E_CONTEXT_EXPIRED` after the PIN has already been entered.
- On **Windows on ARM**, the ARM64 curl cannot load an x64-only vendor
  key-storage provider (certSIGN's Paperless vToken KSP is one), so the
  login fails instantly with `SEC_E_UNKNOWN_CREDENTIALS`, before any
  network traffic.

Both had the same workaround — install Git for Windows, then paste
`C:\Program Files\Git\mingw64\bin\curl.exe` into a settings field — which
asked an accountant to install a developer toolchain to route around
someone else's bug, on exactly the machines least able to diagnose it. A
bundle that already carries a whole CPython can carry a 2 MB curl.

## What the bundle carries

A curl compiled from pinned source during the release build: Schannel-only,
HTTP/HTTPS-only, statically linked with a static CRT — one self-contained
`.exe` with no DLLs beside it and no Visual C++ redistributable to install.
It is not a downloaded binary, because none would do: curl's own Windows
builds (curl.se) are LibreSSL builds with Schannel switched off, and the
Windows key store is the entire point of shipping one.

The source is pinned by release tag *and* by the commit that tag names, so
a moved tag fails the build rather than quietly changing the binary, and
the finished executable has to report that exact version and the Schannel
backend before it is allowed into the bundle. Being an x64 build, it also
answers the ARM case for free: Claude Desktop installs the x64 bundle on
ARM64 Windows and the OS emulates it, so the bundled curl can load the x64
provider the native curl refused.

The **curl program** setting has not gone away — it is now an advanced
override, and your value still wins over the bundled one if support ever
asks you to set it.

## The terminal command is unchanged

`anafpy spv login` from a terminal — the pip-installed CLI, which the setup
walkthrough uses for the first-time certificate selection — still runs the
computer's own curl, and on Windows still wants the Git-for-Windows fix. A
CLI install has no bundle to borrow from. The setup guide's troubleshooting
table now says which surface each fix applies to, in both English and
Romanian.

## Not yet verified

- **A real certificate login through the bundled curl.** Two dry runs on a
  native Windows runner proved the compile, the Schannel backend, the
  stamped version, and the packed bundle — but a login that presents an
  actual non-exportable token key through ANAF's F5 renegotiation needs the
  hardware, and has not been run. The mechanism is right (Schannel is what
  makes the `CurrentUser\MY\<thumbprint>` syntax work at all); the
  end-to-end confirmation is outstanding.
- **Windows on ARM specifically.** The reasoning that an emulated x64 curl
  loads an x64 KSP is the same reasoning that made the Git-for-Windows
  workaround succeed live in July, but it has not been re-confirmed with
  the bundled binary.
