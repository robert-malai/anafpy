# anafpy 0.7.0 — the inbox actually reads

## Fix

**`DownloadedMessage.view` rejected every real inbound document — silently.** Across one operator's e-Factura inbox of 85 downloaded ZIPs, all valid CIUS-RO and all accepted by ANAF at filing, the flat `InvoiceDocument` projection succeeded on **zero**: every document parsed cleanly into the UBL model and then died in the flat-model translation, and because `view` swallowed the error into `None`, the failure looked exactly like "not an invoice". The reader was applying the *authoring* models' construction-time checks to documents coming off the wire — checks whose whole job is to stop you filing an invalid document, re-purposed to judge documents ANAF had already accepted. One rejected optional field cost the whole invoice.

Reading and authoring are now different contracts on the same models. The reader validates through a context marker that stands the consistency and sign checks down while keeping coercion, defaults and normalisation, so the shapes real inboxes are full of read cleanly:

- **A storno filed the Romanian way** — a type-380 invoice with negative amounts throughout, rather than a type-381 credit note (34 of the 85 documents).
- **Empty optional elements** — UBL means `<cbc:PostalZone/>` as *absent*; the models saw a zero-length string and refused it (25 documents). Empty and whitespace-only elements now read as absent, and an optional aggregate left with no identifier at all is dropped rather than taken to mean the document is unreadable.
- **Malformed contact free-text** — two addresses in one BT-43, a telephone of `-` (25 documents). ANAF validates neither field; a typo there is not worth an invoice.
- **A category-O line carrying an explicit zero rate** — read as the redundant spelling of "no rate" that it is (1 document).

What still refuses to read is a missing mandatory element or a value failing one of the ANAF-certain mirrors — the closed code lists, format patterns, length limits and decimal budgets, all rules ANAF itself enforces fatally. Those cannot fire on an accepted document, so a refusal now means one thing: the vendored CIUS-RO edition has drifted, and `schemas/README.md` has the re-vendoring playbook.

**Unreadable no longer means silent.** When the projection does fail on parseable UBL, the cause is kept on the new `DownloadedMessage.view_error` and a `UserWarning` is emitted — "85 invoices archived with every field blank" can no longer happen without a trace. `view` still never raises, and the raw bytes and full UBL model remain the fallback tiers.

**Two authoring checks were wrong, not merely strict, and are relaxed in both directions.** BT-146's non-negativity is gone: CIUS-RO 1.0.9 comments BR-27 out of its UBL binding — the file's own header says "to correct problems regarding negative values for item net price" — so an authored storno with a negative unit price now renders and files like the market's own. And category O accepts a redundant explicit `0` rate as "no rate" instead of refusing it. The document totals also lost their sign constraints entirely: no EN 16931 or CIUS-RO rule constrains them, and 12 of the 85 accepted documents carry a negative VAT total.

**Running the corpus through the fixed reader surfaced two more bugs, both producing spurious *fatal* findings on documents ANAF accepted.** When the accounting currency equals the invoice currency (BT-6 = BT-5 — 48 of the 85 documents), the single `TaxTotal` is both BT-110 and BT-111, but the reader kept only BT-110 and `validate()` flagged a fatal BR-53. And a document spelling category O's absent rate both ways — no `cbc:Percent` on the line, an explicit `0` on the subtotal — had its VAT breakdown group split in two, producing a fatal BR-O-08. Both fixed; the four places that build the breakdown grouping key now share one function.

A smaller edge from the same review: the VAT-identifier prefix check now admits `1A` (Kosovo), the one non-alphabetic prefix on BR-CO-09's own list — previously wrong when authoring and fatal when reading.

**Verified against the corpus**: all 85 real ANAF-accepted downloads read, all 85 render back through the authoring models, all 85 re-render byte-stably, and `validate()` reports zero findings across them — local verdicts agreeing with ANAF's on every document.

Reported as issue #9, from [anaf-sync](https://github.com/robert-malai/anaf-sync), where `view is None` turned every XML-derived path variable into `unknown`.

## Not yet verified

**Filing an authored storno has not been run against ANAF.** The relaxation that allows negative amounts when authoring is grounded in the Schematron source and in 34 accepted inbound documents, and a storno read from the wire re-renders byte-stably — but no negative-value document composed with `efactura.authoring` has been filed to TEST since the change. The library-level `render_invoice` still validates first by default, and ANAF's `validare` remains the authority either way.
