# anafpy 0.11.0 — the extension brings its own Python

The Claude Desktop extension is now **self-contained**: one bundle per
platform, each carrying its own CPython and the complete locked dependency
closure. Installing needs no Python, no uv, and no package resolution over
the network — drag the file into Claude Desktop's Settings, and the public
lookup tools work immediately.

## Per-platform bundles

0.10.0 shipped a uv-type bundle: Claude Desktop's managed uv resolved the
released `anafpy[mcp]` from PyPI at install time. That made the extension's
health depend on the host's uv and on PyPI at exactly the moment an
accountant is installing — and that audience is precisely who cannot debug
either. The bundles now carry everything: the exact CPython the release was
built with (`3.13.14`, pinned in `pyproject.toml` and enforced by the test
suite), the full lockfile closure installed flat, and a manifest that
launches the server as a plain binary — no runtime requirements for the
install dialog to demand.

One bundle per platform, under constant asset names:

- `anafpy-darwin-arm64.mcpb` — Apple-silicon macOS
- `anafpy-darwin-x64.mcpb` — Intel macOS
- `anafpy-win32-x64.mcpb` — Windows (Windows-on-ARM runs this one under the
  OS's built-in emulation)

`releases/latest/download/anafpy-<target>.mcpb` are the stable install URLs
from this release onward; 0.10.0's single `anafpy.mcpb` name retires with
the uv-type bundle. There is no Linux bundle — Claude Desktop, the only
`.mcpb` consumer, does not run there.

Each bundle is built on a native runner of its own platform — a cross-build
would not fail, it would silently carry the wrong interpreter, so the
builder refuses one outright — and the build audits its own output: symlinks
are pruned before packing (the packer materialises each into a full ~18 MB
interpreter copy), the packed archive is size-checked against the stage, and
CI schema-validates all three generated manifests on every push.

## The setup story shrank

With a self-contained one-click install there is no choreography left to
guide, so the `anafpy-setup` plugin is retired (a marketplace tombstone
covers existing installs). The setup walkthrough — English and Romanian — is
restructured around the extension: install the bundle, fill in the settings
screen, ask Claude to log you in. Installing the workflow skills from the
plugin marketplace is now a walkthrough step of its own, and the README
leads with the extension. The hand-edited `claude_desktop_config.json`
route survives as the developer path.

## The release pipeline, held honest

Cutting a release now builds each bundle on its own native runner — the
Intel-macOS leg compiles cryptography from the locked sdist, the one
target PyPI ships no wheel for — after a guards job that refuses a tag
whose version disagrees with `pyproject.toml` or that carries no release
notes. `workflow_dispatch` runs the same builds as a publish-nothing dry
run. Toolchain pins each keep one home: the `.mcpb` packer pin lives only
in `scripts/build_mcpb.py` (CI validates manifests through the script
itself), and the builder interpreter follows `.python-version`.

## Not yet verified

- **The publish leg is first exercised by this very tag.** The three
  native-runner builds were proven by a dispatch dry run, and the
  darwin-arm64 bundle by local builds — but the multi-asset upload and the
  `releases/latest/download/anafpy-<target>.mcpb` URLs go live with this
  release.
- **End-machine installs on Intel macOS and Windows**: both bundles pass
  the build's audits, and the Windows `.pth` replay (pywin32) is covered by
  the staging logic, but a one-click install of the published assets on
  real machines of each platform is what closes this gap.
