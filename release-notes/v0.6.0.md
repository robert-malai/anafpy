# anafpy 0.6.0 — sign declarations on Windows

## Feature

**Declaration signing now works on Windows.** Signing was the last macOS-only step in the declarations strand: everything else — authoring, DUKIntegrator validation and rendering, the portal filing, the public status tracking — already ran on both platforms, but the qualified signature could only be produced through the macOS Keychain, so a Windows user got the validate/render half and had to finish on a Mac. `WindowsStoreRawSigner` closes that: it signs through the **Windows certificate store** (`Cert:\CurrentUser\My`), the same store the SPV client already enumerates, so a certificate that works for SPV works for signing with nothing further installed beyond the token's own middleware.

The raw RSA operation is delegated to the OS exactly as on macOS — anafpy never touches the private key, and the PIN prompt is the middleware's own, which remains the human gate. `platform_raw_signer` picks the implementation, so library and MCP callers are unchanged; the choice of PowerShell over binding `ncrypt.dll` is what keeps it small, because `RSACertificateExtensions.GetRSAPrivateKey(...).SignData(...)` covers a modern CNG/KSP key and a legacy CSP key through one call. DUK's own `-s`/`mscapi` signing stays rejected: it would route the PIN through DUK's process.

**`ANAFPY_SIGN_IDENTITY` is now per-platform.** It takes the Keychain identity name on macOS and the certificate's SHA-1 **thumbprint** on Windows — the same selector `anafpy spv certs` prints and `anafpy spv select` persists, so setting it by hand is usually unnecessary. Selecting by thumbprint also means the ambiguity that macOS has to refuse (two identities sharing a name after a renewal) cannot arise there. A selection made on the *other* platform is ignored rather than mistranslated, so a home directory synced across machines can't feed a Keychain name to Windows.

## Not yet verified

**The Windows signing path has not been run against a real certificate store.** Both signers are covered on every CI leg by a fake of their own platform seam, and the design follows the macOS path that a D406T filing verified end to end on 2026-07-17 — but whether a given token's Windows middleware exposes its key through CNG or a CSP at all is only answerable on real hardware. If it doesn't, the failure is explicit ("the private key is not reachable as an RSA key") rather than a corrupt signature, and the fallback is the validate/render half plus manual portal filing. Two neighbouring Windows legs are unverified for the same reason: a live DUKIntegrator validate/render run, and the declaration portal's certificate login.
