# anafpy 0.6.2 — the DUK staleness report tells the truth again

## Fix

**`declaratie_duk_status` reported every declaration validator as stale, forever.** Right after a clean `declaratie_duk_install` that had just fetched D112's `J26.0.3`, the status report claimed the installed version was `31-Jan-2011 publicat J1.0.0`. The report was not idempotent: nothing you could install would ever make it say "current", so the one signal that tells an accountant whether ANAF's validator is up to date was pure noise — and the advice it drove, "reinstall this form", never helped.

The installed version was read from the first non-blank line of `lib/<FORM>IstoriaVersiunilor.txt`. Those files are chronological, **oldest first**, and their opening lines are free text that varies per form: a document title for D406 (`Istoria versiunilor pentru D406`), a bare date for D212 and D390, and for D100 the first release ever published — `19-Oct-2011 publicat versiunea de test J1.0.0`. So the extracted value was either the oldest `J…` version on record or not a version string at all, and comparing it against the feed's `versiuneJ` could not match by construction.

anafpy's own install manifest already records the feed's `versiuneJ` for every file it fetches, which is why `declaratie_duk_install` reported the right versions in the same session the status tool got them wrong. That manifest is now the authority: `installed_forms()` reads it first and only scrapes the history file for a dist that has no manifest — a hand-assembled one under `ANAFPY_DUK_DIR`, or an install predating the managed installer. The scrape itself now takes the **last** `J<major>.<minor>…` token in the file rather than line 1, and matches the `J` prefix specifically so the PDF jar's `P…` versions on the same lines can't be mistaken for it. Verified against the live feed on a real dist: all twelve preinstall forms report `current`.

The same first-line scrape sat in the SAF-T installer, where it recorded D406T's version into the manifest — so for the one form whose jars come from the `duk_SAFT` archive rather than the feed, the authoritative source was being poisoned at write time. Both paths share one helper now.

**The status report also stops conflating "never installed" with "out of date".** Every form ANAF publishes but this dist doesn't have was flagged `stale: true`, which reads as "you have an old version" when it means "you have none" — and D406T, which ANAF's feed does not list at all, was being judged against a version that doesn't exist. Each row now carries a `state`: `current`, `stale`, `not installed`, `not in feed` (D406T — unlistable, therefore unjudgeable), or `unknown` for an installed validator whose version nothing on disk states. `stale` stays in the row as the plain "an update fixes this one" flag, true for that single state.

Nothing about installing changed. The convergence check compares each file's SHA-256 against the manifest and never went through the broken version read, so repeat installs were correctly skipping current files all along.

Reported as issue #8, from a session where the install and the status tool disagreed about the same twelve forms seconds apart.
