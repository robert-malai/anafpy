# anafpy 0.12.1 — the Windows extension starts

The `anafpy-win32-x64.mcpb` bundle from 0.12.0 could not start its server.
Anyone who installed it saw the extension enabled, question marks scattered
through its description in Claude Desktop's settings screen, and no ANAF
tools. Reinstalling this build over it is the whole fix — nothing else on
the machine needs touching, and the settings you filled in are kept.

## One byte, two symptoms

The bundle's build script generated two files without naming an encoding,
so each was written in the **build machine's** locale codec. The Windows
release runner's is cp1252, which encodes an em dash as the single byte
`0x97` — and both files are read back as UTF-8 on the user's computer:

- `manifest.json` is what Claude Desktop reads to draw the install and
  settings screens. Every em dash in the extension's name and description
  arrived as `�`.
- `sitecustomize.py` is Python source, and CPython decodes source as UTF-8.
  It died at import with `'utf-8' codec can't decode byte 0x97`.

The second one is why nothing worked. That generated file exists for a
single purpose: to replay the `.pth` files in the bundle's library
directory, which entries on `PYTHONPATH` never get on their own. pywin32
lives behind one of those — its modules and its DLL registration both — so
when the file failed to parse, the MCP SDK's Windows helper could not
import `pywintypes` and the server exited during startup. The macOS bundles
were never affected: that runner's locale is already UTF-8, so the same
script wrote the same bytes correctly.

## Why the build did not notice

0.11.0's notes listed the Windows `.pth` replay as covered by the staging
logic. The staging was right; what nothing checked was whether the file
that performs it survives being written. The build now reads both generated
files back **out of the packed archive** and proves they are readable —
`json.loads` for the manifest, `compile()` for the sitecustomize, which
applies CPython's own source-decoding rules. This runs on the release
runner for the target it just built, which is the only place a Windows
bundle's encoding can be judged at all; a bundle that would fail on a user's
machine now fails the release instead. A test tripwire covers the same
ground from any host by refusing text file IO in the builder that leaves
the encoding to the locale.

## Upgrading

Download `anafpy-win32-x64.mcpb` from this release and install it over the
existing extension. The macOS bundles change only in version number — this
release fixes nothing they were suffering from — and the library on PyPI is
unchanged apart from its version, since the bug lived entirely in the
extension's build.

## Not yet verified

- **The Windows start itself.** The traceback confirms every link in the
  chain except the last: the file now parses, so `site.addsitedir` runs,
  so `pywin32.pth` is replayed, so `pywintypes` resolves. That last step
  has been reasoned, not watched — no Windows machine ran this build before
  it was cut. What is certain is that the encoding fault is gone and that
  the build refuses to ship it again.
