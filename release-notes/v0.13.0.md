# anafpy 0.13.0 — a euro invoice, a lei declaration

Romanian filings are denominated in lei. The documents they are built from
often are not, and until now anafpy left that gap for the caller to fill: an
e-Transport goods line wants `value_ron`, an invoice's BT-111 wants a figure
`compute_totals` refuses to derive, D301 wants a `curs_valutar`. This release
fills it from the institution that publishes the rate — `anafpy.bnr` reads
Banca Națională a României's official exchange rates, and the MCP server serves
them as `bnr_fx_rate`.

It is the first non-ANAF source in the project, and it stays deliberately
narrow: it reports what BNR published on a day. It does not rule on which day's
rate a given filing must use.

## Why this is not arithmetic to leave to a model

The alternative was to tell Claude to fetch BNR's XML, find the currency, apply
the multiplier, multiply, and round — per line, into a declaration that carries
20,000–100,000 lei of exposure if the value is wrong. Two things about BNR's
data make that worse than it sounds.

BNR quotes the small denominations **per 100 units**:
`<Rate currency="HUF" multiplier="100">1.4430</Rate>` means 100 forints, not
one. Miss the attribute and the value is out by a factor of a hundred. And the
rounding is fiscal — two decimals, half away from zero, applied once to the
final figure — not Python's default banker's rounding, which would round a
figure ending in exactly .005 the other way.

Both now happen in one place, in code, with the published rate and the day it
was published carried alongside the result.

## Rates exist per banking day, and the answer says which one you got

BNR publishes once per banking day, just after 13:00. A Saturday, a public
holiday, or a call at nine in the morning has no rate of its own — so a lookup
returns the latest rate published **on or before** the day asked for, and
always reports the day it actually served:

```
requested_date: 2026-08-30      (a Sunday)
rate_date:      2026-08-28      (the Friday BNR last published)
fallback_to_last_published: true
```

Presenting Friday's rate as Sunday's is the one mistake this client is built to
prevent, and the workflow skill is instructed to report `rate_date` to you, not
the date it asked about.

## What changes in the e-Transport workflow

The `etransport-declare` skill previously said, when a source document was in
euro: *ask the user for the RON value*. It now converts, and in two places that
matter.

The obvious one is the goods lines. The less obvious one is the very first
question the playbook asks — **does this transport need declaring at all?** That
test includes a total value above 10,000 lei, which is roughly €1,900: close
enough to ordinary invoice sizes that a guessed rate flips the answer. A €1,950
invoice priced at a round 5.0 reads 9,750 lei and looks exempt; at BNR's
published 5.2584 it is 10,253.88 and is not. The skill now converts before that
judgment rather than eyeballing it.

Filing a correction to an already-issued UIT no longer silently re-prices it,
either: re-running the flow days later would restate values you never asked to
change, so the skill asks first and states which day's rate the figures carry.

## For library users

```python
from anafpy.bnr import BnrClient

async with BnrClient() as bnr:
    conversion = await bnr.convert("1234.56", "EUR")
    print(conversion.amount_ron)   # Decimal('6491.81')

    rates = await bnr.get_rates("2026-08-30")
    print(rates.date)              # 2026-08-28 — the banking day served
```

No credentials, no test/prod split. To price several amounts at one rate — an
invoice's lines — fetch the set once and call its `convert` per amount, so every
line demonstrably shares a rate. Full guide:
[exchange rates](https://anafpy.readthedocs.io/en/latest/library/bnr/).

Documents are parsed through models generated from BNR's own published XSD, now
vendored in `schemas/bnr/`, and cached in-process according to what BNR can
still change: a closed year's archive is final and never re-read, while today's
file is re-read every fifteen minutes so a 13:00 publication lands. BNR asks
callers to cache rather than re-fetch, and to read these files instead of
scraping its pages; anafpy does both.

## Upgrading

Nothing to change. The new tool is read-only and works with no login, like the
`anaf_*` lookups. Desktop extension users get it with the next bundle; the
library gains one runtime dependency, `async-lru`.

## Not yet verified

- **Which rate the law requires is not settled by this release.** ANAF's
  e-Transport procedure names no conversion source, and we found no citation
  that mandates the declaration-day BNR rate specifically. That rule lives in
  the workflow skill as a rule of practice, and the figures still pass a human
  at the filing gate like every other value. If your accountant applies a
  different convention, pass the date you need.
- **Whether BNR ever revises a rate it has already published** is unconfirmed.
  Today's file is re-read every fifteen minutes, so a revision would be picked
  up; that is why the cache does not simply hold it until tomorrow.
- The client is live-confirmed against BNR's real feed — today's rates, the
  archives for 2014, 2025 and 2026, and both of the namespaces BNR currently
  serves. A full e-Transport TEST filing built from a converted euro invoice
  has **not** been run end to end.
